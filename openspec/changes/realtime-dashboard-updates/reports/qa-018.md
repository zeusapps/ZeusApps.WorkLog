## Findings

### QA-400: Open reader retains active metadata after external archive move

- Severity: warning.
- Related task / requirement: tasks 2.1, 4.3 and 7.4; [Refresh while preserving reading context](../specs/openspec-browser/spec.md), scenario “Change is archived while open”.
- Location: `dashboard/e2e/dashboard.spec.ts:685` is the failed acceptance assertion; the behavior is served through the selected-document refresh path in `dashboard/src/app.ts`.
- Expected / actual: after the selected change moves into its archive directory, the same document remains readable and its provenance changes to Archived, with review mutations disabled. The rename succeeds, but the open reader continues to show Active and the expected archive transition does not complete within the test timeout.
- Reproduction: `npm run test:e2e --prefix dashboard -- --grep "keeps links working after archiving"` against the current Release output. The test failed after 15 seconds with 33 observations of the Active badge.
- Evidence: independent Playwright reproduction and trace/screenshot under ignored `dashboard/test-results/results/dashboard-keeps-links-work-fa6c0-ors-repeat-no-open-launches/`; current full .NET suite passes, so the defect is specific to browser convergence rather than the corrected coordinator fixture gate.
- Recommended correction: detect when the selected change's archive metadata changes and ensure the selected document refresh obtains authoritative metadata even if its text revision is unchanged; preserve the ordinary unchanged-document fast path when archive metadata is stable. Retain the existing same-document route, text, permissions, and browser recovery assertions.
- Relationship: new QA-400; associated with the canonical archive-recovery blocker identified by the orchestrator.
