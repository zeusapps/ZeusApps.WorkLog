## Findings

### QA-650: Reader status region ignores the grace period and the connecting state
- Severity: warning
- Related task / requirement: 9.2; spec "Brief reconciliation does not flash", ORCH-021
- Location: dashboard/src/app.html:1043-1045 (reader-live), `liveStatusLabel()` in dashboard/src/app.ts
- Expected / actual: A routine reconciliation inside the grace period must not present Reconnecting. The page bar and page announcer honor this, but while the document reader is open the `reader-live` region (role=status, aria-live=polite) renders `liveStatusLabel()` directly. Every reconciliation shows "Reconnecting" for its duration and is announced, and the initial state shows "Connecting…". The docs claim the polite region announces only real changes.
- Reproduction: open a document reader, trigger a revision (journal write); the reader strip flips to Reconnecting and back. Source inspection only; I did not run it in a browser.
- Evidence: inspection of app.html; the existing reader e2e only asserts the label matches Live|Reconnecting|Updates paused.
- Recommended correction: drive the reader label from the same grace logic (for example show Live or the connecting label until `reconnectingLong()`), and cover it with a unit test. Or record the reader as a deliberate exception in the spec.
- Relationship: new; related to ORCH-021 and ORCH-012.

### QA-651: Focus tooltip has no assertion
- Severity: suggestion
- Related task / requirement: 9.2, scenario "Live is unobtrusive" (keyboard users)
- Location: dashboard/e2e/c06-realtime.spec.ts:128-129; dashboard/src/styles.css `.live-indicator:focus-visible::after`
- Expected / actual: The scenario promises the state and refresh time to keyboard users. The test only checks focus; the CSS `::after` tooltip content and visibility are untested (the accessible name is tested, so screen-reader users are covered). The tooltip is anchored to `right: 0` of the indicator and could clip at 390 px; unverified.
- Reproduction: Tab to the indicator at 390 px and look.
- Evidence: inspection only.
- Recommended correction: assert `getComputedStyle(indicator, "::after").content` and that its box is inside the viewport at 390 px.
- Relationship: new.

### QA-652: Retry from Updates paused briefly shows no status bar
- Severity: suggestion
- Related task / requirement: 9.2
- Location: dashboard/src/app.ts effect on `liveStatus` (resets `reconnectingLong` on every change)
- Expected / actual: After Retry, status moves from paused to reconnecting. The paused bar disappears at once and the Reconnecting bar only appears after 2 s, so for about 2 s the header dot is the only cue, and the focused Retry button is removed. Within spec (the grace period applies), but a visible "Retrying…" cue would help the user who just pressed Retry.
- Reproduction: inspection of the effect; the e2e Retry test passes.
- Evidence: inspection.
- Recommended correction: optional; keep the bar while `liveRetrying()`.
- Relationship: new; related to ANALYSIS-705.

## ORCH-023 assessment

The confirmed gap is real: `activateLiveScope` returned when `desired()` was null, so an activation before the first revision loaded nothing. The fix loads the visible journal and Daily when the live connection exists and data is loaded. It does not call markReconciled, so Live still waits for a revision. The unit tests cover all four views and the Live-after-reconcile order, and the docs state that the browser test passes on the old code too (no proof of the user's trigger). The fix is sound for the stated gap. Residual risk: `loadVisibleJournal` runs unscoped by the refresh queue in this branch, so it can overlap the initial start() load once (duplicate fetch, harmless). I did not check the failing-before claim by running the old code; the docs make it and I take it as the developer's statement.
