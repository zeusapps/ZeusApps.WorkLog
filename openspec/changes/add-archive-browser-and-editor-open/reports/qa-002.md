### Investigation 1: `DevInstallTests.PreflightRefusesStaleUnmarkedAndCorruptPackagesAndChangesNothing`

Verdict: environmental (working-tree timestamp ordering), not caused by the change's code. It is deterministic given the timestamps, and it is not flaky in the random sense. It also fails on a pristine checkout of `c53e647`.

Evidence:

1. The assertion expects the stale reason to start with "Source file". The reason comes from `tools/WorkLog.DevInstall/Staleness.cs`: `NewestSource` takes the newest last-write time over the listed input files and also over every input directory under `src`, `dashboard/src`, and `dashboard/scripts`. It reports "Source directory ..." when that newest item is a directory. The test builds a package stamped 2001, so whichever input is newest wins. The test reads the real working tree (`Fixture.Repository` is found from the test assembly location).
2. Working tree of the change: `dashboard/src` (directory) last-write 15:55:21.27 UTC, newer than the newest included file `dashboard/src/app.ts` 15:54:48.95 UTC. `*.spec.ts` files are excluded from file consideration but still bump the directory time when written (the latest write was `app.archive.spec.ts` at 15:55:21.27 UTC, the same instant as the directory). The message in the failing run is "Source directory dashboard\src changed af...".
3. qa-001 passed because at that time the newest input was a file, not a directory.
4. Clean-baseline control: `git worktree add --detach artifacts/qa002-baseline c53e647` (disposable, ignored directory), Release restore/build, then `dotnet test --filter FullyQualifiedName~DevInstallTests`. Result: the same test failed there too, with "Source directory src\WorkLog changed afte...", Not found "Source file" (17 of 18 passed). A fresh checkout writes directory entries as it creates files, so a directory can carry the newest time. The baseline contains none of this change's code.
5. The change's code does not touch `tools/`, `Staleness`, or the test (`git status` shows no `tools/` or `tests/WorkLog.Tests/Updates` changes).

Conclusion: the test is sensitive to mtime ordering between input directories and files in whatever tree it runs in; the result depends on the last edit in each tree (a file saved after the last spec-file or directory change makes it pass). Flaky across environments, not a regression from this change. No fix attempted; the test, not the change, is the place to address it. See the decision below.

### Investigation 2: did the symlink test exercise a file link?

Yes. The test user can create file symbolic links in this environment, and the test cannot have returned early.

Evidence:

1. Probe: a disposable single-file .NET program (run under the same user and shell that ran the test suite, in the scratchpad) called `File.CreateSymbolicLink` for `evil.md` → `tool.cmd`. It succeeded, and `FileInfo.ResolveLinkTarget(true)` returned `tool.cmd`. No privilege error.
2. Mutation proof on a disposable worktree: in `artifacts/qa002-baseline` (baseline plus the change's `src/WorkLog/Dashboard`, `tests/WorkLog.Tests/Dashboard`, `dashboard/src`, `dashboard/e2e`), the new extension check in `EditorOpener.OpenAsync` was disabled (`if (false)`), then `ArchiveAndOpenTests` was run. Result: `OpenOnlyLaunchesMarkdownTargetsEvenThroughFileLinks` failed with `Expected: BadRequest, Actual: NoContent`; the other 10 passed. A test that returned early would have passed. So the link was created and the guard is what rejects it. The real tree was not modified for this.
3. The test file was not modified.

Side effect to disclose: the worktree contained a directory junction to `dashboard/node_modules` for its build; `git worktree remove --force` followed the junction and emptied the main tree's `dashboard/node_modules` (ignored build output). I restored it with `npm ci --prefix dashboard --no-audit --no-fund` (487 packages) before the e2e runs. No tracked or untracked-by-Git content was affected; the identity after the review is unchanged. The worktree is removed and `git worktree list` shows only the main checkout. Residual disposable data: scratchpad probe projects only.
