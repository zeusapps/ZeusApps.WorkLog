Trace evidence (Playwright `trace.zip` network logs, monotonic ms):
- Failure 1: page `GET /api/state` at 99314, test `PUT /api/state` (selection `example/board-demo`) at 99451, then a page-originated `PUT /api/state` at 99705 (about 250 ms later), then the reload `GET /api/state` at 99914 reads the clobbered state (all repositories).

The tests write the state out of band through `page.request.put("/api/state")` while the page that loaded earlier still has a pending debounced save, so the last write wins with stale data.

Judgment: the two failures are one root cause, a lost-update race between the e2e helpers' direct state PUT and the live page's debounced full-document save. It is a test-order/timing defect in the helpers (`open`, and the in-test `stateWith` calls), in the same family as QA-151, not an environment problem and not a defect that affects a single user in normal use (a user cannot write the state behind the page's back). It is real at the product boundary only for multi-tab use, which is out of scope here. CI runs this suite, so the flakiness rate (2 of 8 full runs here, 2 earlier occurrences in S2 and QA-141's run) is a gate risk. See QA-171.

## Findings

### QA-171: Packaged e2e is flaky from a lost update between the helpers' state PUT and the page's debounced save

- Severity: warning
- Related task / requirement: 5.6 (packaged e2e acceptance); extends QA-151 (test isolation); related to S2 and QA-141 history
- Location: `dashboard/e2e/dashboard.spec.ts:1157-1162` (`open`), `:1291-1310` (restores a saved priority order, in-test `stateWith` calls); source of the racing write `dashboard/src/app.ts:1920-1950` (`remember`/`persist`), reviewed at `abe5d5d` plus working tree
- Expected / actual: expected a full packaged run to pass deterministically. Actual: 2 of 8 full runs failed, in two different Ongoing board tests, because a page-originated `PUT /api/state` 40 to 250 ms after the test's own `PUT` overwrote it with the page's stale in-memory state (selected repositories null, previous board order).
- Reproduction: run `npm run test:e2e --prefix dashboard` repeatedly against the packaged 0.4.0 build with `WORKLOG_DASHBOARD_EXECUTABLE` and `WORKLOG_DASHBOARD_NO_NODE=true`; failures occurred in runs 1 and 4 of 8 (first failing tests: `derives columns from recorded facts and expires short-lived cards`, `restores a saved priority order for a card in its column`). Trace network logs show the sequence described above.
- Evidence: traces captured in the reviewer's scratchpad (not committed); sequence timings in the Flakiness section above.
- Recommended correction: make the helpers wait for the page's debounced save before writing state out of band (for example await the page's pending PUT after `authorize`/reload, or poll `GET /api/state` until it equals the written document after a short settle), or write the state before the first page load (`addInitScript`/a navigation after the PUT) so no page holds an older copy; apply the same in the in-test `stateWith` plus reload pairs. Alternatively make the board tests set state through the UI. Do not mask with retries unless the user accepts retries in CI. No product change is needed for single-user use.
- Relationship: same family as QA-151 (test isolation); QA-141 (Daily copy) was not reproduced and is not part of this race; S2's recurrence is the second failing test here.
