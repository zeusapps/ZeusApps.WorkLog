## Findings

### QA-001: Search "unavailable" notices ignore the repository selection

- Severity: warning
- Related task / requirement: openspec-browser "Scoped document search" (distinguish no matches from incomplete or unavailable sources within the selected repositories); work-dashboard "Shared repository selection"
- Location: `src/WorkLog/Dashboard/DocumentService.cs:173` (at 582f8bc)
- Expected / actual: notices should describe only the selected scope. `SearchAsync` seeds `unavailable` from every catalog notice and every errored source before applying the repository filter, so a search limited to one repository reports another repository's missing source.
- Reproduction: in a disposable fixture with repositories `example/worklog` and `example/bell-tower`, rename the bell-tower checkout, then `POST /api/search` with `{"query":"the","repositories":["example/worklog"],"scope":"active"}`.
- Evidence: 20 matches, all `example/worklog`, and `unavailable` contained `example/bell-tower: no available OpenSpec source. Recorded history is still available.` The UI shows this under "Some sources could not be searched".
- Recommended correction: filter notices and errored sources by the requested repositories (all repositories when none are requested) before returning them; add a test with two repositories.
- Relationship: none

### QA-002: Default 30-day History range freezes at the first-visit dates

- Severity: warning
- Related task / requirement: work-dashboard "Ongoing work and history navigation" (History defaults to the last 30 days; changed values are remembered); heuristic "Time passes"
- Location: `dashboard/src/app.ts:959-977` (`remember()` persists absolute `from`/`to`), `dashboard/src/app.ts:200-201` (restored over the default)
- Expected / actual: an untouched default must keep meaning "last 30 days"; only values the user changed should be remembered. `remember()` runs after every history load and stores absolute dates, so the first visit pins the window.
- Reproduction: open History once, wait for the 350 ms save, reopen with the browser date moved 5 days forward (Playwright `page.clock.setFixedTime`).
- Evidence: saved `history` was `from 2026-09-28`, `to 2026-10-27`; the reopened page on simulated 2026-11-01 still showed 09/28/2026 to 10/27/2026 ([screenshot](../screenshots/qa-001-history-range-frozen.png)). The Ongoing view's 14-day window used the real clock and was unaffected.
- Recommended correction: store a relative marker (for example a "last N days" flag) while the user has not edited the dates, and resolve it against the current day in the selected timezone on each visit; persist absolute dates only after an explicit edit. Add a unit test with an injected date.
- Relationship: none

### QA-003: Preferences exceed the 64 KiB cap after hundreds of documents; every later save fails

- Severity: warning
- Related task / requirement: work-dashboard "Dashboard appearance" (theme restored on later visits); heuristic "State grows"
- Location: `dashboard/src/app.ts:576-578` and `:846-850` (per-document `documents` and `positions` entries are never pruned), `src/WorkLog/Dashboard/DashboardState.cs:29` (64 KiB cap)
- Expected / actual: bounded client state, or a visible and recoverable limit. Actual: the state grows with every document opened and scrolled until `PUT /api/state` returns 400 `Dashboard preferences exceed 64 KiB.`; every later `remember()` fails the same way, so theme, repository and range changes stop persisting and the error banner is re-raised on every interaction (behind the reader dialog while a document is open).
- Reproduction: a fixture repository with 800 small changes; in one browser session open each document (client route change per document); then toggle the theme.
- Evidence: after 800 opens `dashboard-state.json` was 61,722 bytes, PUT statuses ended `204, 204, 204, 400, 400`, banner `Dashboard preferences exceed 64 KiB.`; a later theme toggle produced a third failed PUT.
- Recommended correction: cap and evict `documents`/`positions` (for example most recent N entries), and treat an oversized save as a trim-and-retry rather than a per-interaction error.
- Relationship: none

### QA-004: Catalog rediscovery spawns CLI processes every 2 s and blocks document reads for seconds on a large archive

- Severity: warning
- Related task / requirement: openspec-browser "Refresh while preserving reading context", task 3.5 (hash/scan only on change); heuristic "State grows"
- Location: `src/WorkLog/Dashboard/SourceCatalog.cs:29` (2 s cache), `:84` and `:126` (`openspec context --json`, `openspec list --json` per source), `src/WorkLog/Dashboard/DocumentService.cs:86` (every document read awaits the catalog), `dashboard/src/app.ts:211` (2 s poll)
- Expected / actual: opening or refreshing a document should stay responsive as the number of changes grows. Actual: once the 2 s cache expires, the next catalog or document request reruns discovery under a single gate; with 807 changes in 4 sources each discovery took about 7.5 s.
- Reproduction: fixture with ~800 change directories; time `GET /api/catalog` or `POST /api/document` 2.5 s after the previous call.
- Evidence: three uncached catalog calls took 7771, 8230 and 7446 ms; a document read after cache expiry took 7405 ms versus 2-3 ms inside the cache window. With a search term typed, every poll also re-reads and re-hashes every document (`fresh: true`, `DocumentService.cs:183`; about 0.5 s for 800 small documents).
- Recommended correction: make discovery incremental or cache keyed on directory timestamps, run it off the request path (stale-while-revalidate), and avoid forced fresh hashing of every document for search polling.
- Relationship: none

### QA-005: Escape closes the reader while editing a comment and inside the delete confirmation

- Severity: warning
- Related task / requirement: openspec-browser "Keyboard-accessible reading and navigation"; document-feedback "Display existing review comments" (deletion requires a local confirmation); heuristic "Input focus"
- Location: `dashboard/src/app.ts:1018-1030` (global `document:keydown` Escape handler)
- Expected / actual: Escape inside the comment textarea or the delete confirmation must not close the surface being edited. Actual: the handler ignores the focused element and calls `closeDocument()`.
- Reproduction: open a change design, select a paragraph, type text in "Review comment", press Escape; separately click Delete on a note and press Escape.
- Evidence: in both cases the document reader was gone afterwards (dialog count 0), with the confirmation dismissed together with the whole reader. The typed text survives only in the in-memory draft map and is lost on reload; the user never sees a prompt.
- Recommended correction: let Escape act on the innermost surface first (dismiss the confirmation, then cancel or blur the textarea), and only close the reader when no editable control or confirmation has focus or content.
- Relationship: none

### QA-006: Date boundary is wrong for zones with a skipped midnight

- Severity: warning
- Related task / requirement: work-dashboard "Factual elapsed spans and activity dots" (timezone and daylight-saving boundary)
- Location: `dashboard/src/api.ts:47` (`boundary`)
- Expected / actual: `boundary(date, zone)` should return the first instant of the local date. For zones whose clocks skip 00:00, it returns the previous local day at 23:00, so the range includes the last hour of the earlier day (as a lower bound) or drops the last hour of the day (as an upper bound, since `to` is `boundary(to+1 day)`).
- Reproduction: evaluate `boundary('2026-04-24','Africa/Cairo')` and `boundary('2026-03-29','Asia/Beirut')` (script over all IANA zones and all days of 2026, 152,570 cases).
- Evidence: exactly two failing cases: Cairo 2026-04-24 returned `2026-04-23T21:00:00.000Z` (local 23:00 on 04-23) and Beirut 2026-03-29 returned `2026-03-28T21:00:00.000Z`. All other zone/day pairs were correct, including Europe/Warsaw's 2026 transitions.
- Recommended correction: when the computed instant maps to the previous local date, advance to the first valid instant of the requested date; add unit cases for skipped-midnight zones.
- Relationship: none

### QA-010: Literal `-&#45;` typed in a comment is displayed as `--`

- Severity: suggestion
- Related task / requirement: document-feedback "Inline review comments" (marker contains the full comment text)
- Location: `src/WorkLog/Dashboard/ReviewMarker.cs:15` (`Escape`) and `:57` (`Decode`); `dashboard/src/markdown.ts` (`decode`)
- Expected / actual: the full text of the comment survives a save and reload. `Escape` does not escape `&`, but `Decode` replaces every `-&#45;`, so a user comment containing that literal sequence changes meaning on reload (and editing it would store `--`).
- Reproduction: save a comment containing `literal -&#45; text`, then read the note back in the reader.
- Evidence: the saved marker body contained `literal -&#45; and -&#45;>`, where the first sequence is the user's literal text and indistinguishable from an escaped `--`.
- Recommended correction: also escape `&` (or the entity prefix) on save and decode symmetrically; keep legacy decoding for existing markers.
- Relationship: none
