## Findings

### QA-001: Order pruning keeps changes outside the selection but drops other off-selection ranks, against the spec's wording

- Severity: warning
- Related task / requirement: 2.2, 3.3; "Bounded dashboard preferences" (cards no longer on the board are discarded first); deviation 2
- Location: `dashboard/src/app.ts` `applyColumn` (the `live` set built from `fullBoard()` plus every active catalog change); `dashboard/src/board.ts:280` `pruneOrder`
- Expected / actual: the spec says entries for cards no longer on the board are discarded first. Actual: ranks of active changes hidden by the repository selection survive a save, but ranks of ticket and ad-hoc cards hidden by the same selection are dropped, so narrowing the selection and reordering one card silently forgets the user's ticket ranking in other repositories. The two behaviours are inconsistent with each other and the first differs from the literal spec.
- Reproduction: rank a ticket card in repository A; select only repository B; move any card; save; reselect A. The change ranks in A remain; the ticket rank is gone (unit cases cover the change half only: `app.board.spec.ts` "keeps the rank of an active change that the repository selection hides").
- Evidence: source and the two unit cases above; not exercised live.
- Recommended correction: decide with the user. Either (a) amend the spec to say pruning keeps ranks of every active change and drops ranks of archived changes and expired ticket/ad-hoc cards, and preferably also keep rows for cards of other repositories, or (b) follow the spec literally and accept that a narrowed selection loses off-selection change ranks. Keeping the current code with an amended spec is my recommendation, because the data lost under (b) is user effort. The 500-entry cap still bounds growth either way.
- Relationship: developer deviation 2

### QA-002: Ticket and ad-hoc cards are not re-expired while the dashboard stays open without journal activity

- Severity: suggestion
- Related task / requirement: "Ongoing board" (ticket and ad-hoc cards leave the board 7 days after their latest observation); 3.1
- Location: `dashboard/src/app.ts` `fullBoard` (the `now()` call inside a `computed`), `poll()` / `dayRolledOver()`
- Expected / actual: a card should disappear 7 days after its latest observation. Actual: `now()` is not a signal, so the board recomputes only when its inputs change, that is on a journal change or at the next local-day rollover refresh. A card can therefore remain on screen for up to about a day past its expiry. A rollover refresh bounds it, so this is not unbounded.
- Reproduction: unit-level only (source inspection); not observed live.
- Evidence: source inspection.
- Recommended correction: acceptable to leave as is; if desired, bump a signal from the existing day-rollover path or an hourly timer so `fullBoard` recomputes.
- Relationship: none

### QA-003: Ad-hoc cards cannot be created by current tools, so the Ad-hoc scenarios are reachable only from legacy rows

- Severity: suggestion
- Related task / requirement: "Ongoing board" ad-hoc card kind and scenario "Ad-hoc work expires"; deviation 1; proposal motivation
- Location: `src/WorkLog/Journaling` `EntryFactory.Prepare` (not modified by the target)
- Expected / actual: the spec treats ad-hoc cards as a normal board kind. Actual: new observations with neither a change nor a ticket are rejected by `EntryFactory.Prepare`, so ad-hoc cards can only come from older journal rows. The behaviour is implemented and tested through SQLite-inserted rows; no defect in the target.
- Reproduction: attempt `log_work` without ticket or change (not run; stated by the developer and unchanged by the target).
- Evidence: developer note in findings; fixture inserts rows directly.
- Recommended correction: a planning note for the user; consider a spec sentence that ad-hoc cards arise from legacy rows, or a separate change that permits unlinked logging.
- Relationship: developer deviation 1

### QA-004: Preference size at the 500-entry order cap is not tested against the 64 KiB limit

- Severity: suggestion
- Related task / requirement: "Bounded dashboard preferences"; Decision 4
- Location: `dashboard/src/board.ts:7` (`orderLimit`), `DashboardState` 64 KiB limit
- Expected / actual: preferences stay within their storage limit with a full order. Actual: the cap is unit tested, but no test saves a full 500-key order together with 500 positions and documents. Ticket keys are about 70 characters and change keys can be longer with several repositories, so the combined size is plausibly close to the limit.
- Reproduction: not performed.
- Evidence: key format in `board.ts` and `changeKey`.
- Recommended correction: add a test that saves a maximal order plus maximal positions and documents and asserts the payload is below 64 KiB, or lower the retained order if it is not.
- Relationship: none
