## Findings

### ANALYSIS-041: On Linux and macOS, `Contained` trusts a link's resolved target path without checking links inside that path

- Severity: warning (latent: the shipped and CI-validated platform is Windows only, where this was probed and is safe)
- Related task / requirement: 5.1, 5.2; ANALYSIS-001 fix expectation ("escape rejection preserved")
- Locations: `src/WorkLog/Dashboard/SourcePath.cs:53-60` (`Contained`), `:8-21` (`Canonical`), `:62-82` (`MarkdownFiles`: non-link entries below a pushed directory are yielded and pushed unchecked)
- Observation: `Contained` canonicalizes only the link entry. Everything listed below the resolved directory is then trusted as canonical. That is sound only if `Canonical` returns a path with no links left in any component. On Windows it does: `ResolveLinkTarget(returnFinalTarget: true)` uses `GetFinalPathNameByHandle`. Probe 2 confirmed it: a junction to `<root>\other\c\d`, where `<root>\other\c` points outside, is rejected. On Unix, .NET follows the `readlink` chain of the final component only and does not resolve links in the target's parent directories. Take a change-internal symlink `x/a` → `<root>/other/c/d`, where `<root>/other/c` → `/somewhere` and `other/c` lies outside the change tree, so it is never listed. The link then resolves lexically to `<root>/other/c/d`, passes the prefix check, and is pushed. Every Markdown file and subdirectory physically under `/somewhere/d` is then listed and walked recursively on each refresh, with names, lengths, and write times. A target of `/` or a home directory turns this into a full tree walk every 2–4 s. The pre-fix code re-walked every directory and file from the source root, so it reached `other/c` and rejected the change. A malicious repository can carry such symlinks, and git creates symlinks on Unix by default. Content is still protected: `DocumentService.Resolve` uses `Within(change.Directory, …)`, and the lexical target lies outside the change directory, so reads and search of those files are rejected. The weakening affects the listing, the stamps, and the walk cost.
- Proposed improvement and benefit: make `Canonical` return a fully resolved path on every platform. After it resolves a link, restart the walk on `resolved + remaining components` instead of appending to the resolved string, with a hop limit such as 40, and fail closed on a loop. Alternatively, in `Contained`, re-run `Canonical` on the result until it stops changing. The cost is paid only for reparse points, so the measured gain from ANALYSIS-001 is unchanged. This also closes the same lexical-target weakness in `Within` for reads on Unix, which predates the fix.
- Behavior-preservation risks: Windows results must stay identical (probes 1–5). A loop limit is needed for cyclic links. In-source links whose resolved path passes through an out-of-source mount point would now be rejected on Unix, which is the intended strict behavior.
- Evidence type: Windows measured (probe 2 rejects). Unix is a performance and security hypothesis from the .NET runtime's Unix `ResolveLinkTarget` behavior. It is not reproduced, because no Unix .NET environment is available on this host.
- Verification / measurement plan: add a test shaped like probe 2. Use a symlink on Unix and a junction on Windows: a link inside a change pointing to `<root>/other/c/d`, with `<root>/other/c` linked outside. Assert the change is rejected with "escapes". Run it on a Linux runner, or a local Linux `dotnet test`, once the platform is validated.
- Relationship: new; regression introduced by the ANALYSIS-001 fix (non-Windows only).

### ANALYSIS-042: Directory-entry stamps stay stale for a hard-linked Markdown file changed through another name

- Severity: suggestion
- Related task / requirement: 5.2; ANALYSIS-001 fix expectation ("`ContentStamp`, `TaskStamp` unchanged")
- Locations: `src/WorkLog/Dashboard/SourcePath.cs:42-47` (`List`), `:74` (stamp from the entry); `src/WorkLog/Dashboard/SourceCatalog.cs:264-267`
- Observation: NTFS updates a file's directory-index metadata only for the name used to open it. When a Markdown file in a change has a second hard link elsewhere and is changed through that other name, its listed entry keeps the old length and write time. Probe 6c–6e measured 3 bytes against `FileInfo`'s 3,003, still stale after 3 s, and refreshed only by the next read through the listed name. Until then `ContentStamp`, `TaskStamp`, and the catalog revision do not move, so search does not re-run and `openspec list` waits for its 60 s expiry. The open-document poll is unaffected, because `DocumentService.Read` stats with `FileInfo`. An ordinary edit through the listed name, including with the writer's handle still open after a flush, matched exactly (probe 6a/6b). Equivalence on fixtures without links had 0 mismatches.
- Proposed improvement and benefit: accept the limitation and say so in the `List` comment or in design.md's Decision 5 risk note ("hard links changed through another name are detected on the next read or the 60 s round"). Hard-linked OpenSpec documents are unusual: git, editors, and `openspec archive` do not create them. If exactness is preferred, fall back to `FileInfo` for entries whose link count exceeds 1. That needs an extra handle query, so it is not recommended.
- Behavior-preservation risks: none for the documentation option.
- Evidence type: measured (probe 6, Windows 11, NTFS).
- Verification / measurement plan: none beyond the documentation review. With the fallback option, rerun probe 6c and the equivalence check.
- Relationship: new; regression introduced by the ANALYSIS-001 fix (narrow).

### ANALYSIS-043: The start-up timezone probe can stop the whole dashboard on a History-only failure

- Severity: suggestion
- Related task / requirement: 1.2; QA-001 fix; work-dashboard "Invalid timezone" scenario
- Locations: `dashboard/src/app.ts:230-240` (start-up check), `:475-490` (`serverAcceptsTimezone`), `:200-261` (`start()` try/catch); compare `:378-433` (`loadHistory` and `loadOngoing` catch their own errors); `src/WorkLog/Dashboard/DashboardHost.cs:122-123` (status mapping)
- Observation: when the saved zone differs from the server zone, `start()` awaits a timeline request before `ready` is set and before the poll timer starts. `serverAcceptsTimezone` rethrows anything other than a 400: a 503 when the journal is busy or unavailable (`IOException`, `SqliteException`, `InvalidOperationException`), a network error, or a 401. The rest of `start()` is then skipped, so OpenSpec browsing, the catalog, and polling are all dead until a reload. Before the fix, the same timeline failure only produced a History error, because `loadHistory` and `loadOngoing` catch internally. In addition, any 400 is read as a zone rejection, although the host maps every unclassified exception to 400. On cost: the probe adds one journal-reading timeline request at start (only for a non-server zone) and one per accepted zone change. It is per action and adds nothing to the idle poll.
- Proposed improvement and benefit: at start, treat a non-400 probe failure as "not verified". Keep the saved zone, which was verified when it was saved after this fix, and continue start-up so History reports its own error. Optionally, also require the server's rejection text ("Unknown reporting timezone.") before treating a 400 as a zone rejection. Browsing then stays independent of the journal, as before.
- Behavior-preservation risks: the agreed scenario must still hold. A zone the server rejects with a 400 is not remembered, and a saved zone the server rejects is dropped at start. An unverified zone kept after a transient 503 makes the next History query fail visibly, which is acceptable.
- Evidence type: source observation (not exercised in a browser; QA owns the functional check).
- Verification / measurement plan: an Angular unit test in which `info` returns `UTC`, the saved zone is `Europe/Warsaw`, and the timeline answers 503. Assert that `ready()` becomes true, that the poll timer starts, and that the zone is kept. A second test answers 400 with a different message and asserts the zone is not dropped (only with the optional message check).
- Relationship: new; regression introduced by the QA-001 fix. For QA's recheck (A5) to confirm functionally.

## Assessment and limitations

- **Coverage.** Both rechecked findings were verified against the corrected identity, with independent measurement (the round-1 harness rerun against the old build, plus a new harness against the current Release build), an equivalence check against the pre-fix algorithm, and Windows containment probes. The regression review covered `SourcePath`, the `SourceCatalog` discovery and cache code, the three new tests, the QA-001 probe (design and cost only), and the new documentation section.
- **Security equivalence of `Contained`.** On Windows, the new check is equivalent to the old `Within`:
  - Reparse points are walked at every level (change root, archive, change, nested directory, file).
  - Case handling is the same.
  - In-source links resolve once and are de-duplicated.
  - Content reads still go through the full `Within` walk in `DocumentService`.

  It is not equivalent where `ResolveLinkTarget` returns a path that still contains links, which is the case on Unix (ANALYSIS-041, latent). The other difference found is stamp freshness for hard links (ANALYSIS-042).
- **Recommended priority.**
  1. Triage ANALYSIS-041 first, because it is security-relevant even though latent. The fix is small and keeps the measured gain.
  2. ANALYSIS-043, because it is a robustness regression in the QA-001 fix. QA may confirm it functionally.
  3. ANALYSIS-044 and ANALYSIS-042 are documentation-level.
- **Limitations.**
  - No Unix environment with .NET was available; the only WSL distribution is Docker's. ANALYSIS-041 is a hypothesis for Linux and macOS.
  - Absolute timings are higher than the developer's and round 1's because the host was loaded, possibly by the concurrent QA recheck. The before and after runs were interleaved, so the ratios are comparable.
  - No dashboard, port, browser, or real CLI was used. The QA-001 probe was reviewed from source only.
  - Full test suites, `npm test`, and `dotnet format` were not run (QA scope).
- **Writes.**
