## Findings

### QA-001: History timezone validation accepts zones the server rejects, and the bad value is remembered

- Severity: warning
- Related task / requirement: 1.2; work-dashboard "Ongoing work and history navigation", scenario "Invalid timezone" ("without being remembered or sent as queries")
- Location: `dashboard/src/range.ts` `validTimezone` (Intl check only); `dashboard/src/app.ts` `timezoneChanged` and `start()` (reads a saved zone through the same check); server side `ReportingPeriod` zone lookup (`TimeZoneInfo.FindSystemTimeZoneById`)
- Expected / actual: A timezone the dashboard cannot use should be rejected inline and never remembered. Actual: the browser accepts `+02:00` and `America/Ciudad_Juarez`, so the field is accepted, the value is saved to preferences, and the server answers every History query with 400 `{"error":"Unknown reporting timezone."}`. Because the saved zone passes the same client check on start, History fails on every later load until the user retypes a zone.
- Reproduction: `validTimezone("+02:00")` returns true (Node 24 Intl, via a probe copy of `range.ts`). Against the packaged dashboard, `POST /api/timeline` with `timezone: "+02:00"` and with `"America/Ciudad_Juarez"` returns 400 "Unknown reporting timezone."; `"Mars/Base"` is also 400, `"utc"`, `"Etc/GMT+3"`, `"US/Pacific"` and `"EST5EDT"` are 200. I did not drive these through the browser UI (not performed).
- Evidence: probe output from the packaged run on port 47953 (disposable fixture under `artifacts/qa-fdr/`).
- Recommended correction: validate against the server's view as well, for example by sending the first query with the candidate zone and only remembering it after a 200, showing the 400 message inline; and treat a saved zone that the server rejects like an absent one (fall back to `/api/info`). At minimum reject offset-style values (`+02:00`) that Intl accepts.
- Relationship: new

### QA-002: Search read cache thrashes when the corpus exceeds 256 documents

- Severity: suggestion
- Related task / requirement: 5.4 (Decision 7); idle refresh cost requirement
- Location: `src/WorkLog/Dashboard/DocumentService.cs` `Read` (eviction by insertion `Order`, set at read time, hits do not refresh it) and `SearchAsync` (sequential scan of all in-scope documents)
- Expected / actual: Consecutive searches over unchanged files should not re-read them. With more than 256 documents in scope (for example "all changes" across several repositories with many archived changes), a sequential scan evicts the entry it will need next, so every document is a miss and `HashReads` grows by the full corpus on each search. Search only re-runs on a catalog revision change, so this costs per edit, not per idle poll.
- Reproduction: not executed (source inspection only). Add 300 documents, search twice, compare `HashReads`; expected increase about 300 on the second search.
- Evidence: source read of the eviction code at the reviewed identity; the passing .NET test uses a small corpus.
- Recommended correction: size the cache above the in-scope corpus, evict by last use rather than insertion, or avoid hashing when length and write time match.
- Relationship: new
