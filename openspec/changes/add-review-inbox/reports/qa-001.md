## Findings

### QA-001: Task 4.3 idle record omits the CLI refresh round and its counters are invalid

- Severity: warning
- Related task / requirement: 4.3, deviation 9 ("The 60 s idle window missed the CLI refresh round")
- Location: `docs/dashboard-validation.md` section "Idle cost with the overview visible" (reviewed identity `19f5e4ad5594`)
- Expected / actual: Task 4.3 requires the idle measurement from `fix-dashboard-reliability` repeated with the overview visible, and that measurement's per-minute cost includes the single refresh round (8 OpenSpec and 4 git spawns). The record reports 0 OpenSpec and 0 git spawns because the 60 s window missed the round, and its method is not valid for git or for OpenSpec on this machine: the git count filters `child_start` events (git invoked directly emits `start`, so it can never count), and the `openspec.cmd` shim is never executed because `LocalCommand` resolves `node_modules/@fission-ai/openspec/bin/openspec.js` through PATH and runs `node` directly. My first run with that same method over 135 s also reported 0 and 0.
- Reproduction: run the developer's idle script with a window of 135 s (spawns 0 and 0 although two rounds occurred), then with a counting `openspec.js` shim and `start` events of git: 16 OpenSpec and 8 git spawns.
- Evidence: this report, idle row. Corrected result, packaged build, 135 s window with two rounds: 16 OpenSpec (8 per round), 8 git (4 per round), 65 requests all `GET /api/catalog`, 0 overview-related requests. Implementation behavior is fine; only the record is wrong.
- Recommended correction: re-record the 4.3 idle section with a window spanning at least one refresh round, count git by `start` events with argv `git`, count OpenSpec with a shim in `node_modules/@fission-ai/openspec/bin/openspec.js`, and state per-round figures (8 and 4) alongside the 0 overview-related requests.
- Relationship: none

### QA-002: `/api/reads/get` returns 500 for a body without `document`

- Severity: warning
- Related task / requirement: 2.2, error-response heuristic
- Location: `src/WorkLog/Dashboard/ReadBaselineService.cs` `GetAsync` (calls `documents.BaselineKeyAsync(request.Document, ...)` with a null document) and `src/WorkLog/Dashboard/DashboardHost.cs` lines 148 to 150
- Expected / actual: invalid input is rejected with 400 as for `/api/reviews` with a null body, `/api/comments` with `{}`, and `/api/reads/mark` (409/400 paths). Actual: authorized `POST /api/reads/get` with `{}` returns 500 (unhandled null reference). `/api/document` with `{}` returns 404.
- Reproduction: authorized `POST /api/reads/get` body `{}` against the packaged build.
- Evidence: probe output `reads/get {} 500` versus `reviews null body 400`, `comments {} 400`.
- Recommended correction: validate `request.Document` (and the same for `mark`) and throw `ArgumentException` for a missing document; add a host test.
- Relationship: none

### QA-003: Parsed-marker cache (512) thrashes when the catalog has more than 512 documents

- Severity: suggestion
- Related task / requirement: 1.2, design Decision 1, "state grows"
- Location: `src/WorkLog/Dashboard/DocumentService.Reviews.cs` `Markers()` (insertion-order eviction of the oldest entry)
- Expected / actual: a second listing over unchanged files does not reparse. This holds only while the scoped set fits in 512 entries (tested). The client always requests `scope: "all"`, so archived documents count too. With more than 512 documents, each sequential listing evicts the entry it will need next (FIFO over a cyclic scan), so every listing after every catalog revision change rereads and reparses every document. Eviction also scans all entries per insertion. This repository currently has 92 documents, so this is not reached today.
- Reproduction: not executed (source inspection and reasoning); would require a fixture of more than 512 Markdown files and counting reparses via `MarkerParses`.
- Evidence: source reading only; no executed test. No test covers a set larger than the bound.
- Recommended correction: either accept and document the limit, or size the cache to the catalog, or make eviction least recently used; add a test for a set larger than the bound.
- Relationship: none

### QA-004: `/api/reads/get` answers 200 `null` for a document that does not exist

- Severity: suggestion
- Related task / requirement: 2.2, error-response heuristic
- Location: `src/WorkLog/Dashboard/DocumentService.Reviews.cs` `BaselineKeyAsync` (resolves the path but never checks the file)
- Expected / actual: other document endpoints answer 404 `Document is unavailable` for a missing file (`/api/document` and `/api/reads/mark` do). `get` for `nope.md` in a real change, and for `@source`, returns 200 `null`. The client treats `null` as no baseline and then `mark` fails with 404, which it swallows, so there is no user-visible defect.
- Reproduction: authorized `POST /api/reads/get` with a valid change and `path: "nope.md"`.
- Evidence: probe `get nonexistent md 200 null`, `mark nonexistent md 404`.
- Recommended correction: return 404 for a missing document, or document the null answer in the design.
- Relationship: none
