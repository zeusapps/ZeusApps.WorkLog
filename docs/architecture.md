# Code organization

WorkLog has an application executable and a small self-contained Windows launcher. Folders and namespaces group application code by responsibility; the launcher/package contracts, MCP protocol, CLI commands, JSON configuration, and journal schema are the external contracts.

| Area | Responsibility |
| --- | --- |
| `Cli` | Define System.CommandLine commands and typed options, dispatch actions, report application version |
| `Mcp` | Host the stdio server and translate tool calls/errors |
| `Journaling` | Validate logging requests, resolve metadata, coordinate persistence |
| `Persistence` | SQLite connections, schema upgrades/backups, transactional entry storage |
| `Reporting` | Validate periods/options, bound pages, encode continuation, build daily groups and stable work identities |
| `Dashboard` | Read-only journal snapshots, source and document discovery, source-qualified copy selection, local HTTP authorization/lifecycle, bounded search, inline review comments, and private UI preferences |
| `Configuration` | Load/save private settings and define configuration models |
| `Repositories` | Run Git, derive stable repository identities, resolve shared worktree context through the common Git directory |
| `Integration` | Plan/apply private initialization, track ownership, render shared instructions |
| `Integration/Clients` | Preserve and update Codex TOML and Claude JSON/instruction files |
| `Installation` | Validate launcher/payload contracts, immutable manifests, selected versions and stable installation identity; shared validation source is linked into the launcher |
| `Updates` | Discover stable releases, coordinate cached checks, verify bounded nested packages, publish immutable payloads, atomically activate/roll back selection and record outcomes |
| `Infrastructure` | Shared JSON serialization, atomic file replacement, content hashing |

`Program` handles process exit and error reporting. `CliApplication` registers init, serve, update, and dashboard commands; System.CommandLine owns parsing, validation, help, and invocation. Each command composes its application operation, and the serve action forwards cancellation to the host. MCP tools delegate to `Journal`, which prepares entries through `EntryFactory`, persists through `SqliteEntryStore`, and builds queries through the reporting components. Existing journal SQL stays in Persistence; the dashboard has a separate read-only snapshot adapter over the same schema.

The dashboard hosts its private JSON API through the ASP.NET Core shared framework inside the existing self-contained payload. It binds to the explicit loopback address and validates Host, Origin, fetch metadata, and an HttpOnly same-site cookie. A current-user secret persists browser authorization; short-lived one-use bootstrap values authorize launches and never appear in copied document routes. A data-directory lease and authenticated health/launch exchange support repeat launches without another listener. The browser shell is an Angular 21 workspace under `dashboard`; its locked production build embeds HTML/CSS/JavaScript and license notices into the executable, preserving the release file allowlist. Node.js is required only for development/builds. The shared framework replaces the redundant Microsoft.Extensions.Hosting package reference. Package-size evidence is recorded with dashboard acceptance. The only local launch operation is `POST /api/open` (`EditorOpener`): it takes a document identity, a line and a fixed preset, resolves the file through `DocumentService`, builds a `vscode://`/`cursor://` link or uses the canonical path, and starts it through the `IEditorLauncher` seam; `WORKLOG_DASHBOARD_TEST_LAUNCH_LOG` swaps in a recording launcher for tests. `POST /api/activity/changes` reads first/latest observations per change name read-only through `DashboardJournal`. `POST /api/daily` (`DailyService`) returns the digest of the last recorded or a selected earlier local day, its previous and next recorded days, and the current day's items so far from one journal read, reusing `TimelineService.Project` with ticket grouping; which cards appear under Today is decided in the client from the Ongoing board.

`DashboardJournal` opens an existing supported journal for reading without creating or migrating it. `TimelineService` reuses work identity/period semantics and computes full pre-upper-bound lifecycle context for identities with visible activity. Row and observation pages carry a fixed maximum rowid, excluding later backdated inserts. Spans describe first-to-last observations, while dots use local activity dates and details retain completion/subsequent-work events. Day drill-down filters by the reporting timezone before pagination. The API does not change MCP schemas or report cursors.

`SourceCatalog` combines saved contexts, compatible legacy paths, launch checkout, journal identities, and read-only Git worktree discovery. OpenSpec context resolves local or standalone roots, and selected store IDs carry into subsequent list calls. Roots are deduplicated without merging conflicting document copies. Configuration reload failures retain last-valid settings, retry on the bounded refresh cadence, and expose one persistent warning until a successful reload. `DocumentService` checks canonical containment including filesystem links, limits reads to 2 MiB, preserves encodings/line endings during comment insertion, and caches complete reads by metadata/revision. Search reads selected Markdown directly with a 50-match limit and explicit partial-source notices. Active task totals come from OpenSpec rather than a second progress parser; navigation positions are independent of totals.

The Angular reader renders sanitized Markdown with source-line block maps and a dedicated REVIEW marker rule. Its left navigator groups Overview, Specs and Other documents, filters full relative paths, and preserves the selected source-qualified change copy and document target. A narrow-screen selector exposes the same document list; headings and task links live in a collapsible On this page section. The reader disables executable markup and automatic remote resources and preserves comment/edit drafts and reading position during refresh and navigation. Read comparisons use synchronous diff bounds; when the timeout or edit-distance limit is reached, the UI marks the whole current document as one focusable Previous/Next stop instead of presenting an empty precise-diff result. Removed review comments are extracted from the same Markdown block tokens used by the renderer, without rendering or sanitizing the full baseline. Only the current document revision pair is memoized. New markers contain an ID, a preceding-passage reference, a bounded quote, and the comment body; older markers remain readable and editable. The service scans standalone markers outside fenced/indented code and checks their exact text before marker-only edits or deletion. Mutations apply only to active change documents and preserve unrelated latest contents, encoding, and line endings. The supported review workflow waits for external edits to finish; final reread checks and atomic replacement are best-effort safeguards with an accepted remaining race. Current-number task routes are best-effort across document revisions; change routes resolve active or archived directories dynamically. `dashboard-state.json` stores resettable UI preferences separately from shared config and journal data. Browser and service checks use isolated repositories and synthetic observations, including concurrent stdio MCP access.

`QueryRequest.GroupBy` selects report identity independently of SQL filtering. `ReportPager` validates `ticket` (default) or `change` before reading a page and includes the selector in the normalized request fingerprint used by continuation. `ReportBuilder` groups each bounded page by reporting date and `WorkIdentity`: change mode retains existing change-first behavior; ticket mode uses the existing sorted distinct qualified ticket-set encoding regardless of change, falling back to the existing identity without qualified tickets. Repository/provider/scope remain part of ticket identity. Overlapping but unequal ticket sets stay separate and each observation has one group assignment. Unresolved extracted IDs are never qualified using current configuration. Original observations, output shape and report schema version 1 are preserved; flat view still validates the selector but has no groups.

Daily groups can span pages. Consumers merge fragments by `(date, workIdentity)` after complete traversal with unchanged options; fragments are not complete totals or final statuses. Omitted and explicit `ticket` share a fingerprint, while changing modes rejects continuation. The added request property changes older cursor fingerprints, so clients restart queries after upgrading and refresh MCP tool discovery by restarting the client. No journal/schema migration is needed. Existing requests adopt ticket-first groups; explicit `change` retains the previous grouping.

`UpdateCommand` adds explicit check/activate/status/rollback operations. `UpdateDiscovery` coordinates release checks through a shared local cache and runs independently of journal calls. Hints compare available releases with both running and currently selected versions, rereading selection locally so old servers suppress already activated offers. `installedVersion` retains its running-process meaning; `selectedVersion` is additive context. Optional hints retain matching schemas/JSON fallback and the report byte budget without affecting observation identity, report schema or cursors.

`PayloadInstaller` accepts the fixed public repository's ZIP/checksum. `ReleasePackage.ExtractVersioned` enforces an exact nested file allowlist, actual extraction bounds and content hashes. Preparation checks the compiled executable version and probes initialize/tools-list using disposable data. Under a bounded publisher lock, activation rechecks selection generation, publishes a complete payload by same-volume rename and atomically replaces `current.json`. Existing processes hold no installation-wide lease. Previous/all published payloads remain, so launches that read an older selection stay valid without a cleanup race. `current.previous.json` supports recovery; the committed selection is authoritative over an interrupted or stale outcome receipt.

The launcher forwards exact arguments, directory, environment and inherited standard handles, waits for the child and propagates its exit code. A Windows job assigned atomically at process creation keeps payload lifetime tied to its launcher, including forced client termination. Only standard handles are inherited; the job handle is not. The launcher emits diagnostics only to stderr and never interprets MCP traffic. Unsupported launcher/shared-data contracts or schema changes require maintenance. Legacy helper/replacement utilities remain covered by their historical tests, but the CLI no longer dispatches the copied-helper path.

Tools declare output schemas and return native MCP structured content plus backward-compatible JSON text. Tool annotations distinguish additive local logging from read-only local querying. The optional-digest logging path reports safe fixed-category diagnostics through the existing stderr logger, with bounded suppression and sink-failure isolation; MCP stdout remains protocol-only and tool schemas remain unchanged. Equivalent Claude Code and Codex protocol fixtures exercise the shared server path; they are fixture evidence, not native-agent evaluations. See [MCP validation](mcp-validation.md) for the documentation review and protocol checks.

## Dashboard live updates

The dashboard's authenticated same-origin SignalR hub is `/api/live`; it permits WebSockets and Server-Sent Events, with Long Polling disabled. Host, Origin, cookie and secret checks apply at negotiate, upgrade and SSE, and a revoked secret closes active connections at their next revalidation. The embedded client is `@microsoft/signalr` (version pinned in `dashboard/package-lock.json`); its license notice ships in the embedded third-party licenses, so the self-contained package needs no Node.js and no network.

The hub's `Snapshot` invocation returns the authoritative revision vector for catalog, documents, journal, digests and saved reads. The server `DashboardLiveCoordinator` binds bounded filesystem watchers to discovered roots, coalesces hints after a 50 ms quiet period with a 250 ms maximum batch delay, and publishes monotonically increasing domain revisions. A five-second reconciliation checkpoint recovers missed watcher events and rebinds watchers after source changes; watcher overflow and failures cause a full reconciliation. Each connection keeps only its newest pending vector. When a pending vector is replaced, a pending periodic-checkpoint tag (the optional monotonic `checkpoint` field, present only on real checkpoint publications) is preserved on the replacement, so a slow client still sees that a checkpoint covers the dropped generation. Ordinary revisions and `Snapshot` results omit the field. When the host begins stopping, new live connections are refused and registered ones are aborted immediately, so Kestrel's wait for open connections does not hold a graceful shutdown.

The Angular client registers its `Revision` handler before starting SignalR, then invokes `Snapshot` and reports Live only after the affected domains reconcile. Revision vectors are merged and queued while domain reads run; stale responses do not mark a newer target applied. A disconnected connection retries within bounded deadlines, and a failed domain reconciliation stays paused for retry; these client retries are distinct from server checkpoints. Receiving a revision shows the non-Live label (Reconnecting) until its reads finish, then Live again. When a document revision advances while a reads response for the same logical document is in flight, the client retries that request once against the advanced document; a failed or second-changing read remains pending. Navigation, source/rendered mode, search and drafts are preserved while authoritative data updates. The status appears in the main view and in the document reader (`reader-live-status`), each with the last successful refresh time. A visible connected page makes no periodic catalog, document, search or timeline requests; the former poll is removed. Time-dependent board and Daily state is driven by scheduled boundaries (seven-day expiry, local midnight, timezone change, visibility resume), not by polling.

Acceptance uses two independent browser contexts and three tabs/connections: context A has a reader/draft tab plus a target-domain tab, and context B has a target-domain tab. Results and limitations are in [Dashboard validation](dashboard-validation.md#acceptance-status).

`RepositoryInitializer` coordinates initialization. Client adapters add proposed changes to `InitializationPlan`; all adapters validate before the plan writes anything. The plan owns backup creation, concurrent-edit checks, atomic replacement, and partial-failure reporting. Managed instruction blocks and templates are shared between clients.

RepositoryRegistry promotes compatible legacy path records into authoritative `repositoryContexts` keyed by the canonical common Git directory, preserving saved local identities and reporting conflicting nonempty settings. Each context contains a RepositoryConfig, selected-client instruction preferences, and the paths of promoted legacy records retained for recovery. Effective-identity inference considers shared contexts and unpromoted legacy records, preserving ambiguity detection across independent configurations. Git remotes derive identity only for repositories without saved context; they never determine ticket provider/scope or cause independent clones to share settings.

Init plans against a configuration copy, so dry-run and preflight failures do not change in-memory preferences. Paired ticket options update provider/scope without changing extraction patterns. Instruction selection has three states: unspecified uses the saved/default mode, enabled installs managed instructions, and disabled removes only owned blocks. Both adapters always retain their private server registration. Private-target validation follows actual writes, allowing an untouched tracked Claude instruction file when disabled. Exclusions cover owned planned targets even when unchanged, so repeat init can restore missing local exclusions. Preference changes apply to future init runs across worktrees while each run edits only its selected checkout.

LocalSettings preserves raw JSON and patches known typed leaves onto the latest saved document under a per-data-directory writer mutex. Independent changes merge, conflicting stale leaves fail, and unknown nested properties survive. Repository first use and initialization participate in the same coordination; journal initialization happens after the settings lease is released. Dry-run creates no settings files. Loading still supplies a missing case-insensitive bugfix alias without rewriting configuration on read; explicit in-memory edits and stored classifications retain their semantics. Ticket filtering and historical qualification behavior are unchanged.

Day digests are agent-written and server-stored. After `Journal.Log` creates an entry, `DigestService` finds the item's observations (its ticket-grouped work identity) on the machine-local day and, for 2 to 30 of them, `log_work` returns a `digestRequest`; the managed instructions tell the agent to finish the user's request first. `save_digest` derives the item and day from the IDs, requires the set to equal the item's current observations that day, and upserts one row per `(item, day)` into `digests.db` beside `journal.db`. `DigestStore` owns that file with its own `user_version` (1), WAL, busy timeout and a named creation mutex; it is separate so the journal schema and shared-data contract stay unchanged and older servers never open it. A store failure turns digests off for that call, and a newer store version turns them off for the rest of the process; neither affects logging or querying. `DailyService` returns the stored digests of the listed items in `POST /api/daily`, and the client shows a digest only when its covered IDs equal the IDs the line shows, so stale digests stay invisible. A failed optional digest read adds a safe private `digestIssue` status; no issue means the field is absent or null. The client keeps journal observations and fallback summaries visible and shows one inline unavailable indication. The catalog snapshot carries a `digestRevision` (the latest save time, one read-only query) next to the journal snapshot; the live revision vector invalidates Daily on a digest-only change and the client performs a targeted Daily refresh. Digest days use the server's local timezone while the dashboard groups days in the History timezone, so a digest near midnight in a differing timezone may not match and is not shown. See [MCP validation](mcp-validation.md#day-digests-add-day-digests-server-side).

Tests mirror the production areas, with isolated filesystem/Git setup in `Testing/TestWorkspace`. Smoke checks cover native clients, journal acceptance, launcher lifecycle and mixed-version activation. The separate launcher probe is a test-only executable for argument/stream/cancellation checks; it is never in the release ZIP. Authenticated live-agent prompts remain opt-in.

`--updates-only PATH_TO_WORKLOG_EXE` checks a copied bootstrap installation, MCP startup/EOF and offline status. `scripts/package-update-fixtures.ps1` builds actual versions 0.0.1/0.0.2, validates launcher arguments/streams/console cancellation/nested-job behavior, then runs `--versioned-updates OLD_EXE NEW_ZIP`. An original MCP stream stays connected through activation while another starts on the selected version. Cross-version retry/start/cursor/settings behavior, concurrent status/publishers/launches, rollback, failure recovery and old-version retention are exercised without agent CLIs or production profiles. `--versioned-native OLD_EXE NEW_ZIP` additionally verifies retained-payload init and native discovery/health using isolated client homes.
