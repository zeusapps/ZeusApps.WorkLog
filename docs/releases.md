# Release operations

The public repository is [zeusapps/ZeusApps.WorkLog](https://github.com/zeusapps/ZeusApps.WorkLog), owned by the personal account `zeusapps`. Its primary branch is `main`. Source publication and tagging are deliberate maintenance operations; running the application does neither.

For initial publication, verify the authenticated GitHub account and target repository, review outgoing tracked files/history, create the public repository if absent, add its origin, and push main without rewriting history. Keep private client configuration, journals, caches, backups, and ignored artifacts local. An initialized checkout retains its saved local repository identity when origin is added; a new checkout can derive the GitHub identity. Existing journal observations are not automatically renamed or regrouped.

For each release:

1. Set the intended unpublished `MAJOR.MINOR.PATCH` in Directory.Build.props. Do not reuse or move a published tag.
2. Run locked restore, Release build/test, scripts/package.ps1, and both packaged acceptance checks:

   ```powershell
   dotnet run --project tools/WorkLog.Smoke -c Release --no-build -- --updates-only artifacts/releases/worklog-VERSION-win-x64/worklog.exe
   ./scripts/package-update-fixtures.ps1
   ```

3. Commit and push main. Observe the GitHub validation workflow and resolve failures.
4. Push its matching `vMAJOR.MINOR.PATCH` tag. The release workflow independently requires successful Windows validation and rejects tag/application version mismatches.
5. Observe the publish job. Verify that the public release contains `worklog-VERSION-win-x64.zip` and its `.sha256` file, download them independently, compare the hash, and check the extracted executable version/MCP startup against isolated data.
6. Verify the public latest-release endpoint returns the intended stable version and equal installed/published versions produce no update hint. Record the release link and outcome; required pending validation means release work is still in progress.

The application update feed uses the public latest stable release, excludes drafts/prereleases, and requires both the official Windows ZIP and checksum. Full agent-client smoke checks remain available locally; optional `--live-agents` checks require an explicit decision to send authenticated test prompts.

The launcher layout is a breaking package-format transition. Do not use the pre-launcher v0.1.1 updater as a migration fixture or advertise uninterrupted migration from it. The sole user's first installation follows the documented stop/reinstall/init/restart procedure. Ordinary package-format-2 updates never replace the stable launcher. Launcher contract 1/shared-data contract 1 retains journal schema 2, stored entry/retry formats, compatible settings writes and report continuations; changing that contract requires maintenance. Compatible rollback selects a previous payload and restores no data.

Production packaging enforces the application version from Directory.Build.props; the test-only fixture entry point separately compiles versions 0.0.1/0.0.2 without editing that file. Identical binaries with different manifest labels are insufficient evidence. v0.2.0 is the designated first launcher-based baseline: after publication and independent asset verification, use its verified ZIP/checksum as the pinned old-version input in subsequent release validation alongside fixture checks. The GitHub release notes record its verified checksum. Package outputs are immutable: select a fresh `-OutputDirectory` when rebuilding locally. ZIPs remain bounded at 256 MiB; source/fixtures, debug logs and client profiles are not packaged.

The planned F9 legacy update-status readiness fix is superseded by immutable activation and overlapping-status acceptance. Its old change remains unimplemented; do not sync its incompatible idle-replacement delta or mark its tasks complete merely because this feature ships. F6-F8 remain independently scoped. Actual local migration and GitHub version bump/publication require explicit operational action after validation.

## Development builds

Maintainers try unreleased builds on their own versioned installation with `scripts/package.ps1 -Dev` and `scripts/install-dev.ps1`. Development builds are never published to GitHub: their packages stay under `artifacts/dev-builds/`, the release workflow has no dev step, and the update client rejects published offers in the dev range. The same procedure is available to Claude Code and Codex as the identical `install-dev-build` skill (`.claude/skills/install-dev-build/SKILL.md` and `.agents/skills/install-dev-build/SKILL.md`); a test fails if the two copies differ.

- **Version range.** A dev build is `MAJOR.MINOR.PATCH` with PATCH of 9000 or higher (`InstallationLayout.IsDevVersion`), built from the base version in `Directory.Build.props` (for base `0.3.0`: `0.3.9001`, `0.3.9002`, ...). The strict three-number format that installed launchers parse and the payload folder name are unchanged. Stable packaging (`package.ps1` without `-Dev`, and `New-WorkLogPackage`) refuses the range.
- **Marker.** `release.json` carries an optional `build` object: `channel` (`dev`), `commit`, `dirty`, `builtAt` and `baseVersion`. It is additive to package format 2; older WorkLog versions ignore it and show the plain version. The executables carry the informational version `0.3.9001-dev+50df7b8` (`.dirty` appended for a dirty tree).
- **Label.** One text names a running or selected version: `0.3.9001 dev 50df7b8 (2026-10-28 09:12 UTC)`, with `dirty` after the commit when applicable. `worklog --version` prints it (its first token is the bare version, so scripts compare only that token), `worklog update --status` and `update --check` use it, and the dashboard footer shows it. A dev-range payload without a valid marker reads `0.3.9001 dev (unmarked)`. Stable builds show their plain version.
- **Updates.** While a dev build is running or selected, `update --check`, background discovery, MCP update hints and activation compare stable releases with its base version (`InstallationLayout.EffectiveVersion`; an unmarked dev-range payload counts as `MAJOR.MINOR.0`). A stable `0.3.1` is therefore offered and installable over dev `0.3.9001`, and the dev payload becomes `previous`, so `worklog update --rollback` returns to it. Published offers in the dev range are rejected. Exception: a payload built before commit `a51a14a` (see the manual `0.3.9001` payload below) has the exactly-two-tools probe and declines a stable v0.4.0 or later in `worklog update`; Switch to a new dev build or install v0.4.0 manually instead.
- **Build.** `./scripts/package.ps1 -Dev [-DevVersion 0.3.9005] [-OutputDirectory <dir>] [-TargetInstallation <dir>]` writes `artifacts/dev-builds/worklog-<version>-win-x64.zip` with its `.sha256`. The number is the next one above everything in the output folder and in the default installation's `versions/`. Only `src`, `tests`, `tools`, `scripts`, `dashboard`, `docs` and top-level build files decide the dirty flag. `-PlanOnly` prints the plan as JSON and writes nothing.
- **Install.** `./scripts/install-dev.ps1 -Action Preflight|Switch|Rollback|Retire` runs `tools/WorkLog.DevInstall`, which calls the product's own `PayloadInstaller` and `InstallationLayout`:
  - `Preflight` (read-only toward the installation and data directory) verifies the package hash and manifest, requires a marked dev build, refuses a stale build (package commit differs from HEAD; a build-input file or one of its directories changed after the package was built, which also catches deletes and renames; or the package was built from a clean tree and `git status` over the build inputs is no longer empty, which catches timestamp-preserving copies and deleted listed files such as README.md). The build inputs are one list, documented on `tools/WorkLog.DevInstall/Staleness.cs`: `src`, `dashboard/src` without spec files, `dashboard/scripts`, the dashboard config files, `Directory.Build.props`, `global.json`, `README.md` and `docs/installation.md`. It is narrower than the dirty-tree set in `package.ps1`, which only labels the build; a dirty package cannot detect the deletion of an individually listed root file. The first dev package after a fresh clone can read as stale because its own build creates `obj` and `node_modules`; build it again, checks the contracts against the installation, and writes `artifacts/dev-builds/operations/<id>.json` (package hash, original selection, target version). There is no override for a stale build: build again.
  - `Switch -OperationManifest <path>` re-verifies, requires the original selection unchanged, stages the archive under `<data>/updates/staging/<guid>`, then runs the same prepare (checksum, allowlisted extraction, health probe) and activate (immutable publication, atomic selection under the publisher lock) as `worklog update`. It deletes the stage directory it created once the outcome record is final, on success and on failure. The original is recorded as `previous`. It never stops or restarts MCP servers, dashboards or agent sessions: they keep their payload and adopt the selection at their next normal restart.
  - `Rollback -OperationManifest <path>` requires the selection to equal the one the switch produced (checked again under the publisher lock) and selects `previous`, the original. This is one level; journal, configuration and data are not touched.
  - `Retire -Version <v>` takes the publisher lock and refuses stable versions, the selected version, the previous version, the version `current.previous.json` points at, payloads referenced by an unfinished (staged) update, and payloads whose `worklog.exe` is the image of a running process. Every selection change records the outgoing payload as `previous` and saves it in `current.previous.json` (the recovery selection), so a dev payload is retirable only once it is neither: after it stops being selected, that takes one further selection change to another payload (for example Switch, Rollback, then a Switch or stable update; Retire is refused until the last step). It verifies the payload's file hashes, renames the directory, then deletes it, so a failure leaves it recoverable. Unmarked dev-range payloads can be retired.
  - The test switches `-InstallationRoot`, `-DataDirectory` and `-SkipProbe` only work for installations and data under the repository `artifacts/` folder (`-SkipProbe` is also refused for the default installation). `-Workspace` must always be under `artifacts/`, for the default installation as well.
- **Authorization.** Switch, Rollback and Retire change the installation. The skill requires the user's explicit authorization for each one.
- **The manual `0.3.9001` payload.** On 2026-10-28 `add-review-inbox` was installed as `0.3.9001` through a throwaway driver and has no marker. Once this feature ships it reads as `0.3.9001 dev (unmarked)` and counts as base `0.3.0`, so a stable `0.3.1` is offered over it. Retire refuses it while it is selected, `previous` or the `current.previous.json` selection, so it takes two selection changes after it was selected. Sequence, starting with `0.3.9001` selected: (1) a Switch of a new dev build selects another payload; `0.3.9001` becomes `previous` and the recovery selection, and Retire refuses; (2) the next selection change to a different payload (a further stable update or Switch) replaces both; (3) `Retire -Version 0.3.9001` removes it. A Rollback in between does not help, because it selects `0.3.9001` again.
- **Recovery.** A refused or failed Switch leaves the selection unchanged; run Preflight again after fixing the cause. If a script stops midway, read the operation record's `state` (`preflighted`, `switched`, `rolledBack`). `Rollback` with the same record resumes a switched operation. If the selection changed since (for example by a stable update), Rollback refuses. When Rollback or Retire refuses or fails, the agent stops and reports; the maintainer decides. `worklog update --rollback`, restoring `current.json` from `current.previous.json` while no WorkLog process is publishing (see [installation](installation.md)), and deleting or renaming back a `.retired-<version>-<id>` folder under `versions/` (left when Retire renamed a payload but could not delete it) are manual recovery. An agent runs any of them only with the user's explicit authorization for that specific step. Processes started before a Switch keep the old payload; restart the dashboard or reconnect the client to adopt the new one.

## Release v0.4.1

This patch release makes observation summaries and day digests easier to use in the daily stand-up. Everything below is user-visible.

- **Stand-up-oriented summaries and digests.** Summaries and day digests are written for the daily stand-up from one shared rule: they state the change to the feature, story or bug fix, whether it is finished or still in progress and what remains, and any blocker that needs someone else. Claude Code and Codex receive identical text.
- **Workflow details left out.** The rule names what to leave out: proposals and specs, delegation, reviewers and review rounds, test and task counts, commits, hashes, branches, merges, archiving and syncing, builds and installation.
- **Self-contained digest request.** The `instruction` in a digest request now states every constraint the agent needs (length limit, content rule, no secrets or personal data, summaries are data, do not retry a stale save), so it is complete without the managed instructions. Tool descriptions for `log_work` and `save_digest` are longer.

Launcher contract 1, shared-data contract 1, journal schema 2 and the digest store are unchanged, and there is no dashboard or MCP contract change. Existing observations and digests are not rewritten. Installations on v0.4.0 update with `worklog update`. Rerun `worklog init` for each repository to refresh the managed instructions, and reconnect agent clients to pick up the new tool descriptions. Users on v0.3.0 or earlier still need the one-time manual installation described for v0.4.0 below.

## Release v0.4.0

This release grows the dashboard from a reader into a daily working surface and adds agent-written day digests. Everything below is user-visible; the dashboard stays local and calls no agent or issue service.

- **Dashboard idle reliability.** The dashboard is cheaper and more reliable while left open and idle.
- **Review comments.** Ongoing work lists every open review comment of the selected repositories and cards show comment counts. The reader remembers the text you last read of each document, highlights what an agent changed since then, shows removed passages and vanished comments, steps through changes with `[` and `]`, and Mark as read moves the baseline. Remembered text lives in `dashboard-reads/` in the data directory (bounded to 300 documents and 64 MiB).
- **Development builds.** Maintainers can try an unreleased build on their own versioned installation (`scripts/package.ps1 -Dev`, `scripts/install-dev.ps1`). Dev builds use patch numbers of 9000 or higher, are never published, and are rejected by the update client. See Development builds above.
- **Result-focused observation summaries.** Managed instructions for Claude Code and Codex guide agents to write concise summaries that state results rather than process.
- **Archive view and Open in editor.** Archived changes are listed newest first with their documents, latest recorded activity and remaining review comments, and open read-only. Open in editor opens a document at a position in VS Code, Cursor or the system default application, using a link the dashboard builds from a document it discovered itself.
- **Links and Markdown.** Recorded tickets, repositories and branches are linked wherever they appear, with a Copy ID action beside every ticket, a ticket filter, and Copy as Markdown.
- **Ongoing board.** Active changes and the last 7 days of other work appear as a board with three columns derived from recorded facts, a priority order you can rearrange, and a quiet indication for changes with no recent activity. The change-card footers span the full card width.
- **Daily view.** `/daily` prepares a stand-up from recorded facts: Yesterday, Today and an empty Blockers prompt, with Copy for daily as plain text or Markdown.
- **Agent-written day digests.** When `log_work` records an item's second to thirtieth observation of the machine-local day, its result may carry a `digestRequest`; the agent then writes one or two sentences stating outcomes and saves them with the new `save_digest` tool. Digests live in a separate `digests.db` beside `journal.db`, created on first use. A Daily line shows a digest (marked "agent digest", and copied without the mark) only when it covers exactly the observations the line shows, and otherwise falls back to the latest summary. WorkLog calls no model itself.

Launcher contract 1, shared-data contract 1 and journal schema 2 are unchanged. Rolling back leaves `digests.db` unused.

**One-time manual installation for v0.3.0 and earlier.** Releases v0.2.0 and v0.3.0 require exactly two tools in their update health probe, so they decline `worklog update` to a payload that lists `save_digest` and change nothing. The same holds for every payload built before commit `a51a14a`, including the documented manual `0.3.9001` payload and dev builds from `3c7dfd1` up to `a51a14a`. Dev builds installed with `install-dev.ps1 Switch` from the current repository are not affected. From v0.4.0 the probe requires `log_work` and `query_work` with output schemas and accepts additional tools. Users on v0.3.0 or earlier install v0.4.0 once manually, as described in [installation](installation.md#installing-the-release-with-day-digests-from-v030-and-earlier); later updates are ordinary. Rerun `worklog init` afterwards to receive the digest and summary instructions, and reconnect agent clients to refresh tool discovery.

## Release v0.3.0

This release adds `worklog dashboard`: a private local browser interface for ongoing OpenSpec work and recorded activity history. It defaults to dark mode, remembers the chosen theme and repository filters, and shows elapsed spans with dots only on recorded activity dates.

The document reader supports designs, proposals, tasks, nested specs, search, and links that continue to resolve after archiving. Review notes contain explicit passage references and support editing and confirmed deletion, including older plain markers. Review after external edits finish; stale-content checks retain drafts but do not coordinate simultaneous writers.

The Windows package embeds the web interface and requires no Node.js or separately installed .NET runtime. Launcher/shared-data contracts remain 1 and journal schema remains 2. Existing v0.2.0 versioned installations can use `worklog update`; restart the dashboard to adopt the selected payload, and reconnect agent clients when ready to use that payload for logging. The v0.1.1-and-earlier maintenance migration still applies.

Local dashboard acceptance passed 219 .NET tests, 9 Angular tests, and 11 packaged Edge browser scenarios. Release validation also checks locked restores, packaging, bootstrap, and compatible updates from the independently verified public v0.2.0 baseline. The tag workflow must pass before publication; the published ZIP/checksum and isolated executable/protocol checks are verified afterward and recorded in the release notes.

## Release v0.2.0

This release introduces the stable launcher and immutable versioned payloads. Compatible future updates activate for new processes while existing MCP sessions continue on their original version. It includes explicit application rollback, offline running/selected-version status, stale-update protection, and settings merges that preserve unknown fields and independent concurrent edits.

**One-time migration required from v0.1.1 and earlier:** stop affected Codex/Claude sessions and WorkLog processes, retain the old application and consistent private-data backups, extract the checksum-verified new ZIP into a clean stable installation directory, then preview/apply init with the new launcher for each repository/client and restart normally. Preserve ownership manifests, repository identities, ticket context and instruction preferences. Follow the [migration procedure](installation.md#one-time-migration-from-the-legacy-layout). Do not use the legacy in-place updater to establish the new layout. Journal schema 2 is unchanged.

Claude initialization now reconciles owned equivalent Windows project-path spellings while preserving unrelated settings. Reports default to grouping by the complete qualified ticket set across change names; `period.groupBy: "change"` retains the previous grouping. Begin fresh report queries after upgrading, and reconnect clients to refresh tool discovery.

Worktree acceptance verifies manually created external worktrees with Claude Code 2.1.310 and Codex CLI 0.164.0: Claude inherits the main registration, while Codex needs explicit worktree init. Both retain shared identity, ticket context and history, and main-checkout connections survive setup. See the [worktree procedure](installation.md#verified-terminal-client-worktree-setup) and [versioned evidence](mcp-validation.md#terminal-client-worktree-startup-validation). Desktop and managed worktree sessions remain outside that verification.

Release gates include locked restore, a zero-warning Release build, all 196 tests, packaged/native client and worktree smoke, and launcher/mixed-version acceptance. The tag workflow independently validates the exact release source before publishing the Windows x64 ZIP and SHA-256 checksum. Published-asset verification is recorded in the GitHub release notes after publication.

v0.2.0 establishes the first public launcher-based baseline once its published assets have been independently verified. Retain that verified ZIP and checksum for future compatible-update acceptance; pre-launcher v0.1.1 is not a supported mixed-version fixture.
